## 0. 시작하는 법 (Claude가 첫 세션에 할 일)

내가 "MY_DEV_GUIDE.md대로 시작하자"라고 하면 Claude는 다음 순서로 진행한다.

1. **이 문서를 끝까지 읽는다.**
2. **착수 질문을 한 번에 몰아서 묻는다** (5번 형식 — 선택지 + 추천안):
   - 게임 한 줄 설명 · 장르 · 참고 게임 (구조만 참고, 그대로 베끼지 않음)
   - 엔진 · 버전 · 렌더 파이프라인 · 입력 · UI (→ 정하면 "변경 금지")
   - 그래픽 방식 (그레이박스 → 어떤 아트? 2D / 3D / AI 생성 에셋)
   - 핵심 재미 3가지, 핵심 루프 한 줄
   - 한 판 길이 · 승패 조건
   - 원격 저장소 (GitHub) 유무
3. **문서 3종을 만든다** (13번 템플릿): `CLAUDE.md`(작업 규칙) · `GDD.md`(기획) · `TASKS.md`(진행 요약 + 작업 순서 + 일지). 수치가 생기면 `BALANCE.md`.
4. **첫날 체크리스트**를 처리한다:
   - [ ] 폴더 구조를 정하고 CLAUDE.md에 적는다 (규칙 코드 / 엔진 어댑터 / 에디터 도구 / 데이터 / 테스트 분리)
   - [ ] 규칙 코드는 엔진을 참조하지 않는 어셈블리 하나로 (테스트로 검사)
   - [ ] 단위 테스트 어셈블리를 첫 기능부터 만든다
   - [ ] 수치를 담을 데이터 에셋 자리를 정한다 — "코드에 숫자 금지"는 첫날부터
   - [ ] Git 초기화 + `.gitignore`(넓은 패턴 `**/Build/` 금지, 출력 폴더는 루트 기준 경로로) + 에셋 줄바꿈 고정(`.gitattributes`)
   - [ ] 에디터 MCP 연결 확인 (11번)
   - [ ] `TASKS.md` 맨 위 "진행 요약"에 다음 작업을 적는다
5. 나에게 "다음 작업" 후보를 추천안과 함께 묻고 시작한다.

**새 세션 · 다른 PC에서 이어 갈 때**: `CLAUDE.md` → `TASKS.md` 맨 위 "진행 요약" → (다른 PC면) `Docs/진행상황.md` 순으로 읽고, 다음 항목을 확인한 뒤 시작한다. "다음 작업: 미정"이면 후보를 먼저 묻는다.

## 1. 협업 약속 — 나와 Claude가 일하는 방식

**대화**
- 한국어로 대화한다. 나는 1인 개발이다.
- 내 요청은 짧고, 스크린샷 · 대충 그린 그림과 함께 올 때가 많다. 그림에 동그라미 친 곳 = 고칠 곳. 모호하면 추측하지 말고 짧게 묻는다.
- 쉬운 말로 설명한다. 영어 약어 · 내부 용어는 처음 나올 때 풀어 쓴다.
- 오래 걸리는 작업 중에는 **지금 무엇을 하는지 한두 줄로 계속 알린다** (빌드 중, 컴파일 대기 중, 캡처 중 …).

**질문과 결정**
- 설계 결정은 **선택지 2~4개 + 추천안 + 각 선택의 영향**으로 묻는다. 나는 대체로 추천안을 고른다 — 그래도 묻는다.
- 답은 `결정 (YYYY-MM-DD, 사용자): … — 이유` 형식으로 TASKS에 남긴다.
- 사소한 것(관례가 있는 것, 코드에서 확인 가능한 것)은 묻지 말고 정한 뒤 **"정한 것 (Claude, 확인 필요)"**로 보고에 적는다.
- **"이제 괜찮아?" · "적합해?" 같은 질문**에는 먼저 한 줄 판단(예 / 아직 / 조건부)을 주고, 갖춰진 것 · 남은 위험(큰 순서) · 추천 다음 단계를 짧게 준다. 확인 안 한 것은 확인 안 했다고 말한다.

**작업 중 내가 바꿀 때**
- 작업 도중 내가 방향을 바꾸면 (예: "10층에서 끝내줘" → 곧바로 "아니 5층으로, 이어서 하기도 남겨줘") **최신 말이 기준**이다. 이미 한 부분은 새 요구에 맞게 고치고, 바뀐 결정을 `결정 (날짜): ~~이전~~ → 새 값`으로 남긴다.
- "이어서 진행해줘"는 멈춘 지점부터 그대로 계속하라는 뜻이다.

**브랜치 · 병합 (고정 규칙)**
- 한 항목이 끝나면 **작업 브랜치**(`phaseN-내용`)에 커밋하고 보고한다. 지시 없이 main에 커밋 · 푸시하지 않는다.
- 내가 **"main에 병합하고 푸시"**라고 하면: fast-forward 병합 → 푸시 → 작업 브랜치 삭제 → 다음 항목.
- 커밋 메시지: `MM.DD/Phase-항목/PascalCase요약` (수정은 `…Fix`). 한 항목 = 한 커밋.

**테스트 실행 (기본값 — 프로젝트마다 바꿀 수 있음)**
- Claude는 테스트 코드 · 검산 테스트를 **작성만** 하고, **실행은 내가 지시할 때만** 한다. 보고에 "테스트 작성, 실행 안 함"을 적는다.
- 컴파일 오류 확인 · 에디터 Setup 메뉴 실행 · 플레이 모드 확인은 Claude가 한다.
- 작성만 하고 오래 안 돌리면 실수가 쌓인다 → 몇 항목마다 "테스트 돌릴 때 됐다"고 알려 준다.

**완료의 정의**
- 완료 = 테스트 통과 + 확인 방법 안내 + **내 플레이 확인**. 구현만 끝나면 `— 플레이 확인 대기`.

## 2. 문서 체계

| 문서 | 만드는 시점 | 역할 | 꼭 들어갈 것 |
|---|---|---|---|
| `CLAUDE.md` | 첫날 | AI 작업 규칙서 | 개요, 참조 문서 표, 협업 방식(1번 요약), 작업 원칙, 기술 스택(버전 · 확정 날짜), 폴더 구조, **코딩 규칙(시스템별 "이건 여기 한 곳")**, **핵심 설계 규칙(변경 금지)**, 아트 규칙, Git · 환경 요령 |
| `TASKS.md` | 첫날 | 진행 요약 + 작업 순서 + 일지 | **맨 위 "진행 요약"**(최신 상태 · 다음 작업 · 브랜치 · 테스트 수), Phase별 항목, 항목마다 결정 · 구현 · 확인 · 확인 못 함 · 테스트 · 확인 방법 · 피드백, "다른 PC에서 할 일" |
| `GDD.md` | 첫날 | 기획서 | 컨셉, 핵심 재미 3, 루프 한 줄, 규칙, 콘텐츠 목록, 승패, **범위 제외(나중에)**, 아트 방향, 결정 사항(이유), 열린 항목 |
| `BALANCE.md` | 첫 수치 | 수치 문서 | 번호 붙은 수치 표, 데이터 에셋 위치 표(0번), 검산 케이스, 실험 표 |
| `Docs/진행상황.md` | 다른 PC · 새 세션 인수인계 때 | 인수인계 요약 (덮어씀) | 지금 브랜치 · 끝난 것 · 진행 중 · 다음 · 주의할 것 |
| 시스템 설계 문서 (예: `REACTIONS.md`, `Docs/직업_X.md`) | 큰 시스템 착수 전 | 한 시스템 상세 | 규칙 표, 수치, 착수 때 정할 질문, 현재 구현 대조표 |
| 에셋 목록 (예: `Docs/ART_ASSETS.md`) | 외부 · AI 에셋을 받기 전 | 무엇을 · 어떤 규격으로 | 이름 규칙, 크기 · 축 · 원점, 우선순위, 받은 뒤 하는 일, 보정 표 |
| 원본 보존 (`Docs/Source/`) | 받은 원본 기획 · 가이드 | 고치지 않음 | — |

**문서 운영 규칙**
- 문서끼리 **번호로 참조**한다 ("수치는 BALANCE 14번", "TASKS 3-21c").
- 결정 · 변경 · 폐기는 지우지 않고 이어 적는다: `~~이전 값~~ → 새 값 (날짜, 이유)`.
- 코드와 문서가 다르면 **문서를 실제 기준으로 고치고 알린다.**
- CLAUDE.md "코딩 규칙"에는 시스템이 생길 때마다 **"이 시스템은 `클래스` 한 곳, 데이터는 `에셋`, 새 항목 = 표 한 줄"** 형식으로 한 줄씩 더한다. 다음 세션의 Claude가 엉뚱한 곳에 코드를 넣지 않게 하는 핵심 장치다.
- 시연 · 출품용 임시 설정처럼 **나중에 되돌려야 하는 것**은 CLAUDE.md에 굵게 "끝나면 끈다"로 적는다.

## 3. 진행 로드맵 (Phase)

| Phase | 목표 | 완료 기준 |
|---|---|---|
| 0. 세팅 | 엔진 · 구조 · 문서 · Git · 테스트 | 빈 씬, 문서 3종, 테스트 어셈블리 |
| 1. 구조 기반 + 핵심 조작 | 틱 · 이벤트 · 스냅샷 · 난수 · 맵, 플레이어가 "하는 일" 하나 | 그레이박스로 조작이 된다 |
| 2. 시스템 연결 | 자원 · 첫 능력 · HUD | 숫자가 움직이고 화면에 보인다 |
| 3. 콘텐츠 · 규칙 확장 | 핵심 시스템 → 아이템 · 적 · 층 · 직업 … 한 항목씩 | 한 판이 시작해서 끝난다 |
| G. 그래픽 (병행 가능) | 그레이박스 → 실제 아트 | 항목별 |
| 4. 재미 검증 | 멈추고 30분 플레이 → 진단 → 기획 수정 | 진단 기록 |
| 5. 메뉴 · 저장 · UI · 사운드 | 배포 가능한 한 판 | — |
| D. 시연 · 출품 | 시연 모드 · 조작 안내 · 빌드 · 출품 문서 (12번) | 시연 PC에서 한 판 |

**내 방식에서 바뀐 점 (친구 가이드와 다름)**
- 그래픽을 재미 검증보다 **먼저 해도 된다** (결정 2026-10-18). 보이는 결과가 있어야 동기가 유지된다. 단, 그래픽은 **표현 레이어만** 바꾸게 구조를 지킨다 (7번) — 그래서 2D ↔ 3D 전환도 스위치 하나로 되돌릴 수 있었다.
- 큰 방향 전환(예: 3D → 2D 픽셀 → 다시 3D)은 지우지 말고 **스위치로 끄고 남긴다.** 되돌릴 때 비용이 거의 없다.
- 기능은 **참고 게임(예: SPD)의 검증된 방식**을 먼저 따라가고, 수치는 내 게임 규모에 맞게 나눈다 (예: "SPD 공식 그대로 + 공통 나누기 3").
- 콘텐츠는 한 묶음(예: 구역 하나 = 적 4종 + 보스 + 타일)씩 만들고 확인한다.

## 4. 한 작업 단위의 사이클

```
① 문서 읽기 → ② 착수 질문 → ③ 결정 기록 → ④ 구현 → ⑤ 직접 확인 → ⑥ 문서 갱신 → ⑦ 커밋 → ⑧ 보고 → (내 플레이 확인 → 피드백 수정)
```

1. **문서 읽기**: CLAUDE.md의 해당 시스템 규칙, TASKS 항목, 관련 설계 문서.
2. **착수 질문**: 정해지지 않은 것만, 한 번에 (5번).
3. **결정 기록**: TASKS 항목 아래 `결정 (날짜, 사용자): …`.
4. **구현 순서**: 순수 규칙 코드 → 데이터 에셋 · 수치(BALANCE + 검산 테스트) → 엔진 어댑터 → UI · 연출 → 테스트 코드.
5. **직접 확인** (8번): 컴파일 오류 0 → 플레이 모드에서 코드로 진행 → 화면 캡처 → 콘솔 오류 0.
6. **문서 갱신**: TASKS 항목(아래 형식), CLAUDE.md 코딩 규칙 한 줄, BALANCE 표.
7. **커밋**: `git status`로 내 변경만 골라 스테이징 (9번), `git diff --cached --stat` 확인.
8. **보고** (6번).

**피드백 수정**: 내가 스크린샷과 함께 "이상해"라고 하면 같은 항목 아래 `고침 (날짜, 사용자 "원문 요약"): 현상 → 원인 → 수정 · 확인`으로 이어 적고 `…Fix` 커밋.

## 5. 질문 · 결정 방법

- 질문은 선택지로: `A: … / **B: … (추천 — 이유)** / C: …`. 수치 질문이면 기본값과 근거를 같이 준다.
- 한 번에 1~4개 질문, 몰아서. 질문 도구(선택 버튼)가 있으면 그것을 쓰고, 추천안을 첫 번째에 `(Recommended)`로.
- 결정에는 이유를 붙인다 — 상황이 바뀌면 다시 판단할 근거가 된다.
- 떠오른 아이디어는 GDD "범위 제외"에 넣고, 착수하면 그 줄에 "→ 날짜 구현".
- 설계 문서 끝에 **"착수 때 정할 질문"** 목록을 미리 만들어 두고, 착수할 때 하나씩 답을 받는다.
- 핵심 설계 규칙(변경 금지)을 바꾸고 싶어지면 **영향 범위를 표로 정리**해서 묻는다.

## 6. 보고 방법

모든 작업 보고는 이 다섯 가지를 담는다. 짧게, 결론 먼저.

1. **한 일** — 무엇을 바꿨는지 (내가 알아볼 수 있는 말로)
2. **확인한 것** — 컴파일 · 플레이 · 캡처 · 로그 (캡처는 파일로 보내 준다)
3. **확인 못 한 것** — 그리고 왜 못 했는지 (예: "에디터 포커스가 없어 실제 키 입력은 못 넣음")
4. **확인 방법** — 어느 씬에서 · 무엇을 눌러 · 무엇이 보이면 정상
5. **커밋 상태** — 브랜치 · 커밋 해시 · main 병합 여부

추가로:
- 내가 정하지 않았는데 Claude가 정한 것은 **"정한 것 (확인 필요)"**로 따로 적는다.

## 7. 코드 구조 원칙

| 원칙 | 방법 | 얻는 것 |
|---|---|---|
| 규칙과 표현 분리 | 규칙 = 엔진을 모르는 순수 코드(어셈블리 하나), 엔진 쪽은 이벤트를 받아 그리기만 하는 얇은 어댑터 | 테스트 · 그래픽 교체(2D ↔ 3D) · 모드 추가가 쉬움 |

| 데이터 주도 | 수치 · 콘텐츠 · 규칙 표는 데이터 에셋. 새 콘텐츠 = **표 한 줄**, 종류별 분기 코드 금지 | 코드 수정 없이 콘텐츠 추가 |
| 수치 = BALANCE + 검산 | 새 수치는 BALANCE 표 + 같은 값을 검사하는 테스트 | 실수로 바뀐 값 발견 |
| 고정 틱 | 시뮬레이션은 틱으로만, 행동은 비용(틱) 있는 커맨드. 시계(턴제 · 실시간)는 교체만 | 모드 추가가 규칙을 안 건드림 |
| 난수 주입 · 용도별 분리 | 시드 난수, 맵 ≠ 전투 ≠ 아이템 ≠ 연출 | 같은 시드 = 같은 결과, 기능 추가해도 맵 그대로 |
| 상태는 스냅샷 하나 | 저장할 상태는 모두 World에, AI · 시스템은 상태 없음. 새 상태 = 스냅샷 필드 + 버전 증가 + 왕복 테스트 | 세이브 · 되돌리기 · 회귀 테스트 공용 |

| 화면 글은 한 곳 | 모든 한글 문구는 텍스트 클래스 하나(`HudText`) | 문구 수정 · 번역 쉬움 |
| 이벤트로 결합 | 규칙 → 화면은 이벤트 버스로만, "바뀐 것만" | 성능 · 독립성 |
| 바뀔 판정은 인터페이스 뒤 | 시야 · 사거리 · 경로 등 | 교체 비용 감소 |

| 시연 · 임시 스위치 | 시연 모드 등은 인스펙터 스위치로, 끄면 원래대로 | 출품 후 정리 쉬움 |

## 8. 확인 · QA — Claude가 직접 확인하는 법

Claude는 "됐을 것"이라고 말하지 않고 **직접 본 것만 됐다고 말한다.**

1. **컴파일**: 파일 수정 후 에디터 콘솔 오류 0 확인.
2. **플레이 모드 코드 진행**: 플레이 모드에 들어가 UI 모델(`Model.Select/Confirm`)과 디버그 진입점(`DebugNextFloor` 등)으로 판을 진행한다. 에디터 포커스가 없으면 프레임이 안 돈다 → 일시정지 + `EditorApplication.Step()`으로 프레임을 진행.
3. **화면 캡처**: 3D 화면만 = 카메라를 렌더 텍스처로 / UI 포함 = `ScreenCapture` + 프레임 진행. 캡처는 나에게 파일로 보낸다.
4. **QA 플레이**: "버그 체크해줘"면 처음부터 끝까지(타이틀 → 모든 층 → 승패 → 기록 → 저장/이어하기 → 모드별) 코드로 진행하고, 버그는 고치고 결정이 필요한 것은 "참고 (결정 필요)"로 남긴다.
5. **빌드 확인**: exe를 창 모드로 실행 → 로그(`Player.log`)의 예외 검사 → 창 캡처 → 실제 마우스 클릭 · 키 입력으로 흐름 확인(포커스를 가져와 OS 입력 이벤트로) → 저장 파일 생성 여부 확인 → 종료.
6. **확인 못 한 것은 그대로 적는다**: 실제 키 입력, FPS, 다른 PC 사양, 전체화면 등.

**알게 된 함정**
- 플레이 중에 스크립트를 고치면 재컴파일로 상태가 날아간다 → 글 수정은 플레이를 끝내고.
- 반투명 UI 배경은 리니어 색 공간에서 생각보다 훨씬 비친다 (0.88도 뒤 글자가 다 보임).
- 같은 캔버스에서 나중에 만든 UI가 위에 그려진다 → 맨 위여야 하는 창은 정렬 덮어쓰기(켜진 뒤에 설정).
- 메모리에 열린 씬은 디스크 YAML 수정이 무시된다 → 씬 값은 에디터 API로 바꾸고 저장.

## 9. 안전 규칙 — 내 데이터와 다른 작업을 지키기

- **다른 세션의 변경을 커밋하지 않는다.** 같은 폴더에서 여러 Claude 세션이 동시에 일할 수 있다. 커밋 전 `git status`로 내 항목 파일만 골라 스테이징한다. 섞인 파일은 hunk 단위로 골라 스테이징.
- 브랜치를 옮길 때 다른 세션의 미커밋 변경과 충돌하면 체크아웃하지 말고 **브랜치 참조만 옮긴다** (fast-forward 가능할 때 `git branch -f main <브랜치>` → `git switch main`).
- 빌드는 작업 폴더 그대로 들어간다 → 다른 세션의 미커밋 변경이 있으면 **빌드 전에 나에게 묻는다.**
- **내 저장 데이터를 건드리지 않는다.** 테스트용 세이브 슬롯은 따로 쓰고(예: 4 · 5번) 끝나면 지운다. 승리 · 기록이 남는 테스트 전에는 기록 파일(명예의 전당 등)을 백업하고 끝나면 복원한다.
- 삭제 · 덮어쓰기 전에는 대상을 먼저 확인한다. 변수로 만든 경로로 지우지 않는다.
- 제품 이름 · 회사 이름을 바꾸면 저장 위치가 바뀐다 → 바꾸기 전에 알린다.
- 의도하지 않은 변경(동적 폰트 에셋 글자 데이터, 줄바꿈만 바뀐 설정, 플레이 중 저장된 설정)은 커밋 전에 되돌린다.

## 10. AI 에셋 파이프라인

- **목록 먼저**: 에셋 목록 문서에 이름 · 규격 · 우선순위 · "받은 뒤 할 일"을 적고 만든다.
- **표 한 줄 원칙**: 모델 크기 · 방향 보정은 Setup 스크립트의 표 한 줄, 새 모델 = 줄 하나 추가 + Setup 메뉴 다시 실행.
- **데이터는 비주얼을 ID로만 참조**: 프리팹이 없으면 그레이박스 도형으로 그린다 → 에셋이 늦어도 게임은 돈다.
- 3D 모델 (예: Varco): 원본은 `Art/<도구>/`, 표시용 프리팹은 Setup 메뉴가 만든다. 묻힌 텍스처 이름이 겹치면 꺼낼 때 이름을 바꾼다.
- 애니메이션 (예: Mixamo): 뼈 이름이 다르면 Humanoid 리타깃. 이동은 코드가, 애니메이터에는 파라미터만.
- 이미지 (UI · 아이콘 · 일러스트): 흰 배경 시트는 가장자리에서 배경색을 지우고 덩어리로 자른다 (스크립트는 `Tools/`). 원본은 그대로 두고 잘린 파일을 따로.
- 이펙트: 키 → 프리팹 · 크기 · 색 표, 없는 키는 조용히 건너뜀. 팩 효과는 길이 · 크기를 맞추고 시간대별로 캡처해 확인.
- 내가 직접 만든 디자인 · 에셋을 우선 쓴다. 다른 게임의 캐릭터 · 아트를 그대로 가져오지 않는다.

## 11. 작업 환경 · Git · 에디터 · MCP 요령

**Git**
- 커밋 전 `git status` → 내 파일만 `git add` → `git diff --cached --stat`.
- 문서처럼 다른 세션과 같은 파일을 고칠 때: 내 부분만 hunk로 골라 스테이징하거나, HEAD 사본을 만들어 내 수정만 넣고 `git update-index --cacheinfo`.
- 여러 PC: pull 후 에디터에 열려 있던 씬은 디스크에서 다시 연다. 인수인계할 때 `Docs/진행상황.md`를 덮어쓴다.

**에디터 MCP (Unity 기준)**
- 파일을 바꾼 직후 첫 호출은 "연결 안 됨"이 나기 쉽다 → 가벼운 호출(콘솔 읽기)로 깨우고, 컴파일이 끝난 뒤 무거운 호출.
- 긴 작업(빌드 등)은 요청이 시간 초과돼도 에디터에서 계속 진행된다 → 에디터 로그(`Logs/Editor.log`의 "Build Finished")와 출력 폴더로 확인.
- 스크립트 실행 도구에 제한(리플렉션 금지, 중첩 클래스 문제)이 있으면 최상위 클래스로 쓰거나 임시 에디터 스크립트를 만들고 지운다.
- 에셋 이동 · 삭제가 확인 창 때문에 막히면 `git mv` / `git rm`(메타 파일 함께) 후 Refresh.

**셸 (Windows)**
- CRLF 파일은 sed/perl 치환이 잘 실패한다 → 편집 도구로.
- 대기는 `sleep` 대신 조건 감시(Monitor) · 백그라운드 실행.
- zip은 Windows 내장 `tar.exe -a -c -f out.zip --exclude …`.

### 13-2. TASKS.md 진행 요약
```markdown
## 진행 요약 (YYYY-MM-DD 기준 — 새 세션은 여기부터 읽는다)
**최신 (날짜): (끝난 것 한 줄) — 브랜치 `…`, main 병합 여부, 테스트 N개 (마지막 실행 날짜), 플레이 확인 대기 목록. 다음: (다음 항목 또는 "미정 — 후보를 먼저 묻는다").**
```

### 13-3. TASKS.md 항목
```markdown
- [x] **N-M. 항목 이름** (YYYY-MM-DD 사용자 "요청 원문 요약") — 플레이 확인 대기
  - 결정 (YYYY-MM-DD, 사용자): A안 — 이유
  - 구현: `클래스`(역할) · 에셋 `경로` · 메뉴 `경로`
  - 정한 것 (Claude, 확인 필요): …
  - 수치: BALANCE N번
  - 확인: 컴파일 오류 0 · 플레이(코드 진행) … · 캡처. 확인 못 함: …
  - 테스트 작성, 실행 안 함: `Tests.이름`
  - 확인 방법: (씬) 플레이 → (조작) → (보이면 정상)
  - 피드백: 현상 → 원인 → 수정. 검사: (다음에 같은 실수를 찾는 법)
  - 고침 (날짜, 사용자 "…"): …
```
